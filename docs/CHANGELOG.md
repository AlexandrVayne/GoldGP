## v2.8.3 / LootMaster v0.7.4 / Flask v0.1.2 — «Женские формы классов: „Шаманка" без иконки» (предыдущая)

Дата: сессия по выводу `/gg classdiag` (v2.8.2), присланному пользователем.

### Диагностика сработала — причина найдена точно

Вывод `/gg classdiag` на ruRU-клиенте (19 игроков, 9 уникальных строк класса,
whitelist 10 токенов):

```
«Шаманка» ×1 → ??? НЕ МАПИТСЯ  (пример: Электробабка)
«Шаман»   ×1 → SHAMAN          (пример: Fillinrullez)
```

**Корневая причина:** клиент WoW возвращает имя класса **С УЧЁТОМ ПОЛА
ПЕРСОНАЖА**. `GetGuildRosterInfo` / `UnitClass` для женского шамана дают
«Шаманка», женского ханта — «Охотница», женского жреца — «Жрица» и т.д.
В мапе `LOCALIZED_CLASS_TO_TOKEN` были только мужские (базовые) формы, а
рантайм-достройка через `GetClassInfo(i)` тоже возвращает ТОЛЬКО базовые
формы — женские строки не могли попасть в мапу в принципе. Итог:
`NormalizeClassToken("Шаманка")` → nil → `class_data` пуст → нет ни иконки,
ни цвета класса.

Это объясняет ВСЮ историю симптома:
- «Шаманка» без иконки, «Шаман» с иконкой — пол персонажа, а не класс;
- «у одних хантов есть, у других нет» — мужчины «Охотник» (мапился),
  женщины «Охотница» (нет);
- «присты/шаманы/ханты криво» — именно те классы, у которых в гильдии есть
  женские персонажи (в этом ростере оба жреца — мужчины, поэтому «Жрец» мапился).

**Фиксы (GoldGP_Storage.lua):**
1. В мапу добавлены ВСЕ женские формы ruRU: Воительница→WARRIOR,
   Паладинка→PALADIN, Охотница→HUNTER, Разбойница→ROGUE, Жрица→PRIEST,
   **Шаманка→SHAMAN**, Чернокнижница→WARLOCK, Друидка→DRUID. («Маг» и
   «Рыцарь смерти» в ruRU одинаковы для обоих полов — записи не нужны.)
2. Hardening рантайм-достройки: цикл `GetClassInfo(i)` больше НЕ обрывается
   на первом nil (раньше первый же nil убивал ВСЮ достройку; в Lua 5.1 нет
   continue — заменено на if).
3. Самосбор формы СВОЕГО класса: `UnitClass("player")` добавляет в мапу
   локализованную строку самого игрока, если её там нет (если игрок —
   женщина, это будет женская форма). Подстраховка для кастом-клиентов.

**Фиксы (GoldGP_Core.lua, classdiag):**
4. Закрыто последнее слепое пятно диагностики: игроки, у которых сервер
   НЕ вернул строку класса вовсе (`class = nil`), раньше МОЛЧА пропускались —
   получалось «не мапится=0, всё ок» при человеке без иконки. Теперь выводится
   отдельная строка: «Без строки класса: N (примеры: ...)» с советом /gg refresh.

Проверки: luaparse (Lua 5.1) 19/19 OK.

## v2.8.2 / LootMaster v0.7.4 / Flask v0.1.2 — «Цикл зависимостей .toc: модули грузились раньше ядра» (предыдущая)

Дата: сессия по репорту пользователя после установки v2.8.1 (фласки не появились,
настройки LootMaster не вернулись, иконки классов всё ещё кривые).

### Корневая причина проблем 1 и 2 — ЦИКЛ ЗАВИСИМОСТЕЙ В .TOC (критический)

**Анализ (подтверждён git-историей):** в v2.8.0 в `GoldGP.toc` была добавлена
строка `## OptionalDeps: GoldGP_Flask, GoldGP_LootMaster`. При этом модули сами
зависят от ядра (`## Dependencies: GoldGP` у Flask; `## OptionalDeps: GoldGP` у
LootMaster). Получился ЦИКЛ: ядро →(optional)→ модули →(hard/optional)→ ядро.
На клиенте пользователя загрузчик разрешал цикл в пользу optional-ребра —
**модули стартовали РАНЬШЕ ядра**. Оба главных файла модулей начинались с
`local Addon = GoldGP; if not Addon then return end` — и **молча отключались
навсегда**:

- `GoldGP_Flask.lua` не исполнялся → `Addon.Flask = nil` → кнопки «Фласки» нет,
  диагностика ядра честно сообщала «загружен, но не инициализировался»;
- `GoldGP_LootMaster.lua` не исполнялся → глобаль `GoldGPLootMaster` не
  создавалась → `GoldGP_LootMaster_Options.lua` выходил на строке
  `if not LM then return end` → **настроек нет, ошибок нет** (и весь
  LootMaster был мёртв целиком);
- `GoldGP_Flask_Options.lua` выходил на `if not Flask then return end` →
  вкладки «Настои» тоже не было.

Именно поэтому фиксы v2.8.1 (динамическая кнопка, регистрация панелей без
офицерского гейта) не помогли: файлы модулей вообще не исполнялись.

**Фиксы:**
1. `GoldGP.toc` — строка OptionalDeps УДАЛЕНА (плюс комментарий-предупреждение
   «никогда не добавлять модули в OptionalDeps ядра»). Порядок загрузки
   обеспечивают .toc самих модулей.
2. `GoldGP_LootMaster.toc` — зависимость от ядра стала ЖЁСТКОЙ:
   `## OptionalDeps: GoldGP` → `## Dependencies: GoldGP` (без ядра LootMaster
   бессмыслен; жёсткая зависимость гарантирует порядок на любом клиенте).
3. **Защита от повторения (boot-обёртки + waiter):** все 5 файлов, которые
   раньше могли молча умереть на раннем гейте, теперь ПЕРЕЖИВАЮТ нарушенный
   порядок загрузки и доинициализируются, как только появится ядро:
   - `GoldGP_Flask.lua` — тело в `boot(Addon)`; если `GoldGP` нет — waiter
     (ADDON_LOADED/PLAYER_LOGIN + OnUpdate до 30с), затем boot + сообщение
     «инициализирован отложенно»; при таймауте — громкое сообщение с причиной.
     БД инициализируется прямо в boot (SavedVariables доступны уже при
     исполнении файла — ADDON_LOADED-ожидание было лишним);
   - `GoldGP_Flask_Options.lua` — тело в `boot(Addon, Flask)`, waiter ждёт
     ядро И модуль;
   - `GoldGP_LootMaster.lua` — глобаль `GoldGPLootMaster` создаётся ВСЕГДА
     (до boot), тело в `boot(Addon)`, пост-инициализация (InitLMDB + префиксы +
     InitClient/InitML + ApplyButtonLabels) выделена в `PostLoadInit` с защитой
     от двойного запуска; отложенный путь вызывает `LM:_PostLoadInit()`
     напрямую (ADDON_LOADED этого аддона уже прошёл);
   - `GoldGP_LootMaster_Client.lua` / `GoldGP_LootMaster_ML.lua` — тело в
     `boot(Addon, LM)` + waiter; в отложенном пути сами вызывают
     `LM:InitClient()`/`LM:InitML()`, если `LM.db` уже готов (в нормальном
     пути `LM.db` ещё нет и вызов остаётся за main — двойного запуска нет ни
     в одном из путей);
   - `GoldGP_LootMaster_Options.lua` — `register_options()` ре-резолвит `Addon`
     на момент регистрации (файловая локаль могла быть захвачена при
     отложенном старте).
   Результат: при ЛЮБОМ порядке загрузки пользователь получает работающие
   модули + внятное сообщение в чат, а не тишину.

### Проблема 3 — «Иконки классов криво работают: ханты, присты, шаманы»

**Анализ (глубокий):**
- **Присты:** известный кварк ruRU-клиента — `GetClassInfo` даёт «Жрец», а
  гильд-ростер (`GetGuildRosterInfo`) возвращает **«Прист»**. В мапе
  `LOCALIZED_CLASS_TO_TOKEN` (Storage) был только «Жрец» → у ВСЕХ прист не было
  ни иконки, ни цвета класса.
- **Ханты «у одних есть, у других нет»:** токен класса у хантов, побывавших в
  рейде офицера, брался из `state.raid_units` (`GetRaidRosterInfo` возвращает
  английский fileName — авторитетный источник), остальные ханты зависели от
  мапы ростера. Плюс **класс альта копировался от мейна** (ParseNote) —
  хант-альт воина показывал иконку воина («криво»), а самолечение v2.8.1
  распространяло класс мейна на альтов вместо собственного класса альта.
- **Шаманы:** та же группа причин — строка ростера вне мапы / наследование
  класса мейна. Точный состав строк сервера покажет новая диагностика.

**Фиксы (GoldGP_Storage.lua, GoldGP_Core.lua, GoldGP_Slash.lua):**
1. В мапу добавлен алиас `["Прист"] = "PRIEST"` (комментарий с объяснением кварка).
2. **Runtime-достройка мапы по данным самого клиента:** при загрузке Storage
   `GetClassInfo(i)` (i=1..20, в pcall) дополняет `LOCALIZED_CLASS_TO_TOKEN`
   локализованное имя → английский токен. Это покрывает любые локали и
   кастом-клиенты (Sirus), где строки ростера совпадают со строками
   GetClassInfo, но не с hardcoded-таблицей.
3. **Класс альта больше НЕ копируется от мейна** (ParseNote): альт — отдельный
   персонаж со своим классом; свой класс приходит из ростера, при его
   отсутствии GetClassToken в UI резолвит авторитетные источники.
4. **Самолечение классов переписано:** на каждом полном проходе ростера
   восстанавливаем класс ТОЛЬКО из живых источников СОБСТВЕННОГО класса
   (`state.raid_units[name]` — токен из GetRaidRosterInfo; для группы — живой
   `UnitClass`), без наследования от мейна. O(N) раз за проход, raid_units — O(1).
5. **Неизвестная строка класса теперь видна пользователю:** однократное
   `PrintError` с текстом «выполните /gg classdiag и пришлите вывод» (раньше
   warn уходил только в скрытый лог).
6. **Новая команда `/gg classdiag`** (read-only, разрешена и вне гильд-лока):
   печатает локаль клиента, размер whitelist'а токенов, ВСЕ различающиеся
   строки классов из гильд-ростера (RAW, как их вернул сервер) с результатом
   маппинга, счётчиками и примерами по игрокам, итог «не мапится: N». Вывод
   копируется и присылается разработчику — по нему добавляются недостающие
   строки. Для команды Storage экспортирован `Addon.DebugNormalizeClassToken`.
7. Текст подсказки «Фласки» обновлён (сообщение про отложенный старт 30с).

### Задача 5 — «Глубокий анализ: иконки классов не у всех (присты/шаманы/ханты)»

**Анализ (по коду):** `class_data` пишется ТОЛЬКО из прохода гильд-ростера:
`LOCALIZED_CLASS_TO_TOKEN[class] or class`. Три пути потери класса у части
игроков (при одинаковых классах у одних иконка есть, у других нет):
1. `class = nil` от `GetGuildRosterInfo` (сервер/кэш клиента) → в class_data
   записывался nil, причём на КАЖДОМ проходе заново;
2. альты: `ParseNote` перезаписывал класс альта значением мейна — если класс
   мейна в тот момент nil, свой валидный класс альта ЗАТИРАЛСЯ;
3. вариант локального имени, которого нет в таблице (кастом-клиент) →
   в class_data попадала сырая строка → `CLASS_ICON_TCOORDS[string]` = nil.
Атлас и координаты иконок корректны (иначе бы пропадало у ВСЕХ).

**Фикс (многослойный):**
- **Storage:** `NormalizeClassToken()` — trim, таблица локалей, ASCII-upper
  fallback, проверка по множеству валидных токенов `Addon.CLASS_TOKENS`
  (заполняется в UIKit из `CLASS_ICON_TCOORDS`); валидное значение БОЛЬШЕ НЕ
  перезаписывается невалидным (nil с сервера не стирает класс); неизвестные
  строки логируются один раз (`Log:Warn`, диагностика кастом-клиентов);
- **Storage:** `ParseNote` альт-ветка — класс мейна копируется ТОЛЬКО если
  валиден (свой класс альта не затирается);
- **Storage:** в конце КАЖДОГО полного прохода ростера — самовосстановление
  классов альтов из мейнов (O(alts));
- **Core:** новый `Addon:GetClassToken(name, main)` — авторитетная цепочка:
  `class_data[name]` → `class_data[main]` → живой UnitClass (рейд:
  `state.raid_units[name]`, снимается в `RAID_ROSTER_UPDATE` из
  `GetRaidRosterInfo(...,6)` — fileName = английский токен; группа: UnitClass
  по unitid);
- **UI UpdateRow:** иконка/цвет теперь через `Addon:GetClassToken` (было —
  только `class_data[name]`).

### Бонус-фикс — краш whisper-фильтра на каждом шепоте

`msg:lower():trim()` в `standby_filter` — **`string.trim` НЕ существует** в
Lua 5.1/WoW 3.3.5a (старая находка аудита, не была исправлена) → Lua-error на

## v2.7.0 / LootMaster v0.7.0 — «Стабильность и честность данных»

Дата: 2025 (сессия правок по итогам полного аудита)

### Баг 1 — СТИРАНИЕ СТАТУСОВ «В ОТПУСКЕ» ПРИ КАЖДОМ ЛОГИНЕ (критический)

**Суть:** `GuildRoster()` — асинхронный. `CleanupOldData()` при входе в мир запускал чистку
`on_leave` по ЕЩЁ ПУСТОМУ кэшу гильдии → все vacation-статусы удалялись из SavedVariables
на каждом логине. Дополнительно `ParseNote` стирал флаг памяти для любой ноты без маркера.

**Фикс (3 слоя):**
- `GoldGP_Core.lua` — `CleanupOldData`: чистка on_leave выполняется ТОЛЬКО когда ростер
  реально распарсен (`Storage:IsInitialized()`). Если ростер ещё не пришёл — чистка
  откладывается; новое событие `RosterReady` (файрится из Storage после первого полного
  прохода) запускает `RunDeferredOnLeaveCleanup()`.
- `GoldGP_Storage.lua` — `ParseNote`: маркер `[ОТП]` найден → флаг ставится и в память,
  и в `db.global.on_leave`; маркера нет → флаг в памяти СОХРАНЯЕТСЯ, если он есть в db
  (снятие отпуска — только осознанно через UI).
- `GoldGP_Core.lua` — `SetOnLeave`: alt резолвится в main; отпуск теперь пишется
  в офицерскую ноту маркером `[ОТП]` (append/strip) — статусы видны ВСЕМ офицерам,
  а не только на локальном клиенте.

### Баг 2 — ДВОЙНОЕ СПИСАНИЕ GP ПРИ ПЕРЕДАЧЕ ЗВАНИЯ МЛ (критический)

**Суть:** `EndLootSession` копировал необработанные `gpPending`-записи в аварийную очередь
`recoveryQueue`, но оригинал в lootTable оставался непомеченным. При повторном входе как МЛ
(или после /reload) `FlushPendingGP` начислял GP из lootTable И из recoveryQueue.

**Фикс:**
- `GoldGP_LootMaster.lua` — `EndLootSession`: после копирования в recoveryQueue оригинал
  помечается `cand.gpProcessed = true` (долг живёт только в очереди).
- `GoldGP_LootMaster_ML.lua` — `RestoreLootTable`: тот же перенос при рестарте после
  логаута (раньше recoveryQueue заполнялась только при смене МЛ — гап при выходе из игры).

### Баг 3 — ЗАВИСАНИЕ ОЧЕРЕДИ ВЫДАЧ + ЛОЖНЫЕ ВЫДАЧИ (высокий)

**3а. «Призраки» в очереди pendingAwards.** Отменённый/просроченный лут оставлял lootKey
первым в очереди — `PeekPendingAward` вечно возвращал его, валидация падала, а ключ
не удалялся → все последующие выдачи того же предмета этому игроку молча блокировались.

**Фикс:**
- `ScheduleLootCleanup` (ML) — при удалении лута из lootTable ключ вычищается и из очереди
  (`LM:PurgePendingAwardByLootKey`);
- `OnChatMsgLoot` — невалидная запись очереди УДАЛЯЕТСЯ и поиск продолжается через fallback
  (раньше — `return` без удаления);
- TTL 10 минут на записи очереди (`LM.pendingAwardsAt` + `LM:PurgeStalePendingAwards`)
  — страховка от любых других утечек.

**3б. Ложные начисления GP.** `CHAT_MSG_LOOT` срабатывает на ЛЮБОЕ получение предмета
(сам лутнул с трупа и т.п.), а не только на выдачу МЛ. Совпадение itemID+игрок считалось
выдачей МЛ.

**Фикс:** валидация свежести — если лут-сообщение отстаёт от `giveTime` выдачи больше чем
на 90 сек, GP не начисляется (WARN в лог + сообщение офицеру).
